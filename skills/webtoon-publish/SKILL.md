# 보드 · 메이킹북 · 공개

`python3 ${CLAUDE_PLUGIN_ROOT}/scripts/build_site.py <폴더>` 가 웹툰, 보드, 메이킹북 페이지를 만든다. 공개 전에는 `--only board` 로 보드만 만든다. 그러면 이미 만든 첫 화면, 웹툰, 메이킹북 파일도 지운다.

| 주소 | 내용 |
|---|---|
| `/` | 세로 스크롤 웹툰. `done` 컷과 아직 고치기 전의 `fix` 컷이 나온다. `project.json` 에 `home` 이 있으면 작품 첫 화면이 나오고 웹툰은 `/read/` 로 옮겨 간다 |
| `/board/` | 진행 단계, 막별 컷 표, 쓴 크레딧, 앞으로 들 크레딧 |
| `/making/` | 인터뷰, 이야기, 캐릭터, 다시 그린 전후, 단계별 크레딧, 시행착오 |

웹툰 제목 아래 오른쪽의 장식 점 세 개 중 마지막 점이 단추다. 디자인 요소처럼 보이고 색만 살짝 다르다. 누르면 컷 번호가 나타나 고칠 컷을 번호로 말할 수 있다. 다시 누르면 사라진다. 상태는 쿠키에 저장한다.

## 보드

산출물이 나올 때마다 `stages` 를 고치고 다시 올린다. 진행을 알리거나 완성 검토를 받을 때는 카톡에 긴 글을 붙이지 말고 링크 한 줄을 보낸다. 부탁할 문장은 `ask` 에 적는다. 손님에게 그림 없는 설계로 컨펌받지 않는다. 손님이 원할 때만 보여 준다.

## 결제 전 맛보기

- 결제 자리는 캐스팅 뒤, 인터뷰 앞이다. 문구는 `dream-webtoon` 운영 설정의 결제 안내 문구를 그대로 쓴다. 결제 전에 그리는 것은 캐스팅 그림(시안 6장, 고칠 곳을 반영한 시트 1장)뿐이다.
- 인터뷰를 다 한 뒤에 처음으로 돈 이야기를 꺼내지 않는다. 이유: 실컷 이야기한 뒤 「더 보려면 내세요」는 배신처럼 느껴진다.
- 웹툰 일부를 보여 주고 잠글 때 가장 어두운 컷에서 끊지 않는다. 이유: 화가 난다. 일상이나 기억처럼 편한 자리에서 끊는다.

## 완성 뒤 검토와 수정

- 검수가 끝나면 완성 웹툰 링크와 그림이 든 스토리보드를 함께 보낸다. 스토리보드는 보드(`/board/`)에 컷 번호가 보이는 것이다.
- 「바꾸고 싶은 컷을 번호로 알려 주세요」라고 묻는다. 피드백은 컷 번호로 받는다. 예: 「17번, 웃는 얼굴로」.
- 수정은 무료 3번이다. 한 번에 여러 컷을 말해도 한 번으로 센다. 받은 날, 컷 번호, 무엇을 `consent.md` 에 적는다.
- 고칠 컷은 `status: fix` 로 바꾸고 그 컷만 다시 그린다. 3번을 넘기면 운영자에게 넘긴다.
- 46컷보다 적은 웹툰을 보낼 때는 끝에 한 줄 덧붙인다: 「지금 이야기로 N컷이 나왔어요. 조금 더 들려주시면 들려주신 만큼 늘려 드릴게요(최대 46컷)」. 40컷 이상이면 빼도 된다. 한 번만 말하고 조르지 않는다.
- 완성 뒤 컷 늘리기는 수정 3번에 세지 않고 따로 한 번이다. 이유: 고치는 일이 아니라 새 재료로 이야기를 넓히는 일이다. 방법은 `story-plan` 의 컷 늘리기(보조)를 따른다.

## 후기

수정이 끝나면 따뜻하게 묻는다. 시험지처럼 늘어놓지 않고 한두 개씩 묻는다.

- 인터뷰는 어땠는지 ★1~5
- 웹툰은 어땠는지 ★1~5
- 한 줄 후기
- 마음에 든 컷 번호

예: 「마지막으로 여쭤봐도 될까요? 인터뷰는 별 몇 개였어요? 제일 마음에 든 컷 번호도 궁금해요.」 답하지 않으면 다시 조르지 않는다. 받은 답은 `consent.md` 에 적는다.

## 공개 동의

- 셋 중 하나를 고르게 한다: 이름 그대로 / 별명 / 공개 안 함.
- 동의 전에는 링크를 아는 사람만 본다. 페이지는 noindex 그대로 둔다.
- 별명이면 제목과 페이지의 이름을 별명으로 바꿔 다시 빌드한다.
- 공개 안 함이면 링크는 본인에게만 두고, 랜딩 · 공유 카드 · 다른 방에 쓰지 않는다.
- 후기를 랜딩이나 공유 카드에 써도 되는지도 함께 묻는다.

## 릴레이

마지막에 「이 웹툰을 선물하고 싶은 한 사람이 있으세요?」를 가볍게 한 번 묻는다. 강요하지 않는다. 없다고 하면 고맙다고만 하고 끝낸다. 알려 주면 `consent.md` 에 적고, 그 사람에게 연락하는 일은 운영자가 정한다.

새 프로젝트의 첫 배포 전에 `site_url` 을 적는다.

## 메이킹북

- 인터뷰는 본인 말 그대로 싣는다. 민감한 답과 뺀 내용은 싣지 않는다.
- 쓰지 않은 사진 원본은 싣지 않는다.
- 크레딧은 그림별로 풀어 적고, 시작 잔액과 지금 잔액을 대조해 `cost_notes` 에 적는다. Claude 토큰은 재지 않았으면 재지 않았다고 쓴다.
- 시행착오는 숨기지 않는다. 그게 읽을거리다.

## 공개 전

1. `check_project.py <폴더> --publish` 실패 0.
2. `webtoon-qa` 검수.
3. `consent.md` 와 맞대어 뺄 내용, 이름, 사진 범위를 확인.
4. 인터뷰한 본인이 완성본을 보고 OK, 그리고 공개 동의(이름 그대로 · 별명 · 공개 안 함). 승인자의 OK 만으로 공개하지 않는다. 미성년자면 보호자도.
5. 공개 범위를 말한다. 링크를 아는 사람은 누구나 볼 수 있다. 페이지는 검색에 나오지 않게 설정돼 있다.

배포는 사람이 허락한 곳으로만 한다.

처음 한 번 프로젝트를 정한다. 사람마다 다른 영문 이름을 쓴다. 이유: 이름 없이 올리면 폴더 이름 `site` 의 프로젝트에 덮어써서 앞 사람의 웹툰이 사라질 수 있다.

```
cd site && vercel link --yes --project <영문-이름>
```

그다음부터는 이렇게 올린다.

```
cd site && vercel deploy --prod --yes
```

배포 직후에는 잠깐 옛 페이지가 보일 수 있다. 1~2분 뒤에 모든 주소가 열리는지, 휴대폰 폭에서 가로 넘침이 없는지 확인한다. 아티팩트로 올려도 되지만 이미지가 많으면 Vercel이 편하다.

## 내리기

본인이나 승인자가 내려 달라고 하면 묻지 않고 내린다.

```
vercel project remove <영문-이름>
```

링크를 공유한 방에도 알린다. 힉스필드에 올린 사진과 그림은 사람이 직접 지운다.

## 공유

- 카톡 메시지는 짧게, 링크 하나.
- 모은 후기는 공개 동의를 받은 것만 랜딩 · 공유 카드에 쓴다. 이름은 고른 대로(이름 그대로 또는 별명) 쓴다.
- 완성 약속을 한 방에 먼저 알린다. 다른 방은 허락 없이 보내지 않는다.
- 긴 PNG 한 장은 그 폭에서 페이지 높이를 재고, Chrome 헤드리스의 창 높이를 그 값으로 잡아 찍는다. 작으면 끝이 잘리고 크면 빈 여백이 남는다. 지연 로딩을 빼고 찍는다. macOS `sips -c` 는 가운데를 기준으로 잘라 위아래가 함께 사라지니 쓰지 않는다. 양쪽 끝을 눈으로 확인한다.
- Iris 로 이미지를 보낼 수 있지만, 여러 장을 한 번에 보내면 순서가 섞여 보일 수 있다. 순서가 중요하면 링크로 보낸다.

## 테스트 시나리오

- 정상: 빌드 → 점검 → 검수 → 완성 링크 + 스토리보드 → 「5번, 12번 바꿔 주세요」 → 고쳐서 다시 올림 → 후기 → 공개 동의(별명) → 릴레이 → 공유.
- 오류: 수정 4번째 요청 → 운영자에게 넘긴다.
- 오류: 후기는 받았지만 공개 동의가 「공개 안 함」 → 후기를 랜딩 · 공유 카드에 쓰지 않는다.
- 오류: 결제 전 맛보기가 가장 어두운 컷에서 끝남 → 끊는 자리를 앞으로 옮긴다.
- 오류: 뺄 내용이 메이킹북에 있음 → 공개를 멈추고 고친다.
